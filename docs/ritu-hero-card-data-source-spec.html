1. Overview

A period start date can enter a user's record two ways: logged live (daily check-in, added the day it happens) or manual (typed in from memory — the onboarding "last period" question, the optional "past dates" step, or the Settings "Add a date" recovery flow). Both count identically toward classification eligibility. They are not treated identically when deciding how confident the hero card is allowed to look.

3.1 Unpredictable still passes through the same data-trust gate

Unpredictable never attempts a phase calculation, for any data source — that part of Section 3.1's original reasoning was correct and is unchanged. But trusting the classification result itself is a separate question from trusting a phase calculation, and Unpredictable does not get a pass on that. If anything it deserves the same bar or higher: it is the most consequential label the app can assign (permanently removes the phase strip, changes tone across the whole home screen, can carry a doctor-flag connotation) — assigning it off nothing but remembered onboarding dates would show a heavy conclusion without having watched a single real cycle.

Resolved rule: Unpredictable follows the identical gate as Regular and Variable — the hero card stays Neutral until both classification is eligible AND one full cycle has been logged live (both endpoints Logged). Only once that gate opens does the result (Regular / Variable / Unpredictable) decide which of the three treatments displays:

Classification resultCard once the gate opens
RegularConfident
VariableHedged
UnpredictableMenstrual card (period days) / Honest card (all other days)

The number of cycles she must log live before this gate opens follows the exact same table as Regular/Variable — see Sections 8–9 — regardless of which of the three results she eventually gets. The manual-date count determines the wait; the classification result only determines which card appears once the wait is over.

4. Rule 1 — Neutral Card Duration

The neutral card shows for every user until both of the following are true:

  1. Classification minimum is met — 3 completed cycles / 4 total period start dates (Manual or Logged, either counts).
  2. At least one full cycle has been logged live in the app — both its start and end date came from real-time daily logging, not memory.

Whichever condition is satisfied later is what the user is waiting on. This closes the edge case from Section 8 below: a user who enters 4 manual dates at onboarding satisfies condition 1 immediately, but still sees the Neutral card until she personally logs through one real cycle in the app — condition 2 is never skipped, regardless of how much manual history she supplies.

6. Rule 3 — Confident vs. Hedged Card

Once both conditions in Rule 1 are satisfied and the Neutral card ends, the underlying Regular / Variable / Unpredictable math has already run (per the Classification Spec) using every date, Manual or Logged. What date source changes is display only:

Confident card shows once at least one completed cycle in the active window has both endpoints Logged — which, per the updated Rule 1, is guaranteed to already be true the moment the Neutral card ends. So for a user's first resolved card, it goes straight to Confident (if the math says Regular) — there is no separate Hedged stop at initial unlock.

Hedged still applies later in the app's life — see 6.3.

6.1 Why a manual date affects two cycles, not one

A manual date is a shared boundary — it is simultaneously the end of the cycle before it and the start of the cycle after it. Both adjacent cycle lengths inherit the reduced confidence. Do not implement this as "only the cycle that starts on a manual date is affected."

6.2 Self-resolving over time

Because classification always uses a rolling window (max 6 cycles, per the Classification Spec), a Manual date eventually ages out of the window as real logging accumulates. No extra flag or reset logic is needed.

6.3 When Hedged still shows, after initial unlock

Rule 1's "one clean cycle" gate only guarantees a clean cycle exists the first time the card leaves Neutral. Later in the app's life, a user can use the Settings "Add a date" recovery flow (e.g. after a data gap, reinstall, or forgotten log) to insert a new Manual date. If that Manual date lands inside the current 6-cycle rolling window and no other cycle in the window is fully clean, the hero card drops back to Hedged until a new clean cycle is logged. This is the ongoing mechanic Hedged exists for — not the initial-unlock moment, which Rule 1 now always resolves straight to Confident.

10. Decision Log

Every user must log at least one full cycle live in the app — both endpoints Logged, not Manual — before the hero card leaves the Neutral state, regardless of how many manual dates were supplied at onboarding or whether classification math is already eligible. This is now captured as part of Rule 1 (Section 4) and reflected throughout Sections 6, 8, and 9.

11. Edge Cases — Inactivity & Missing Data

The rules above assume a user who logs each new period reasonably close to when it happens. This section covers what the hero card does when that assumption breaks — no period date exists yet, she stops logging after a while, or a classified user's expected next period stops arriving on schedule.

11.1 No period date entered at all

A user can skip the onboarding "last period" question entirely (Screen 4's "Skip — I'll log from today"). In this case there is no period start date in the system, so there is nothing for the day-count math (today − last period date) to calculate from.

Rule: show a distinct empty/welcome state — no day number, no "days into your cycle" copy, since both are meaningless without a start date. Copy: "Log your first period to get started." This state is stable, not a countdown — it looks identical whether she skips for 1 day or 30; nothing about it should imply lateness, since there is no baseline yet to be late against.

The moment she logs her first period date, the day counter begins fresh at Day 1. Because this first date came from a live log rather than memory, it is tagged Logged, not Manual — meaning this path is automatically the cleanest possible start (the "0 manual dates" row in Section 8's reference table).

11.2 Has a period date, but stops logging afterward

This is a distinct case from 11.1 — a start date exists, so day-count math is valid, but the user stops opening the app or logging further entries. The key correction: two different counters power the card, and only one of them should be affected by inactivity.

ElementDriven byBehavior if she stops logging
Big number ("14 days into your cycle")Calendar math: today − last period dateKeeps incrementing — this is always accurate and requires no logging to calculate
Right-side text ("2 weeks logged")Count of actual daily log entries she has madeFreezes at whatever she last actually logged — must not climb with elapsed time, since "logged" is a factual claim about what she did
Concrete example: she logs daily for exactly 1 week, then goes quiet. Checking back on day 42: big number shows 42 ("42 days into your cycle" — true, calendar-wise). Right-side text still shows "1 week logged" — frozen, because that is the true amount of history that exists. It resumes climbing only once she logs again.

Soft nudge, pre-classification only: once elapsed days pass a soft threshold (recommend ~45 days with no new period logged), soften the card's tone — e.g. "Log your next period when it starts," right-side text switching to "No pattern yet." This is copy softening only, layered on top of the frozen logged-days counter above; it must never claim "overdue," since pre-classification there is no personal average yet to be late against (see Section 11.3 for when "overdue" language is appropriate).

11.3 Classified user's expected next period doesn't arrive (Regular/Variable "Overdue" fallback)

Once classified, this is the mirror image of Phase-Range Spec Tier C (a cycle too short for the phase formula). Here the cycle is running longer than the model can responsibly extrapolate — most visibly, a Regular/Variable user reaches what should be her Luteal phase and no next period arrives, so there is no new cycle to reset into.

ClassificationTrigger for fallbackWhat shows
RegularDay count exceeds her personal average cycle length (C)Drop the phase strip and phase name. Reuse the neutral card component with cycle-specific copy: "This cycle is running longer than usual." Last period date stays visible; right side reads "No phase estimate."
VariableDay count exceeds the longest cycle in her recorded rangeSame fallback — do not stretch the hedge further into an extended "~Day 40+"; switch to the same neutral "running longer than usual" treatment rather than implying false precision.
UnpredictableNever triggersNo change needed — the existing Honest card ("X days since last period," no day number, no estimate) already absorbs any length of gap gracefully. This is a strength of that design, not a gap to fix.
Why this doesn't affect her classification: one long cycle is exactly the kind of single outlier the Classification Spec already protects against — MAD averages all 6 deviations specifically so "one outlier is smoothed into the result rather than dominating it." This fallback only changes what this cycle's card displays, not her Regular/Variable label.
Self-resolving: the moment she logs the next period date, the cycle closes, the day count resets to 1, the Menstrual card shows immediately, and the long cycle's actual length becomes one more data point feeding the next classification pass — no manual reset or extra flag required.

11.4 A classified user stops logging regularly (general case)

This is 11.3's parent case, stated generally: once classified, the hero card recomputes day count and phase automatically every day from her most recent period start date and her personal C (Regular) or range (Variable) — no new input is required for the phase strip to advance day-to-day. Daily mood/symptom logging lapses do not affect the hero card at all (that only affects Insights/Journal). Only a lapse in period-date logging matters here, and it resolves to whichever of the two outcomes above applies: the Overdue fallback (11.3) if she's within one cycle's overdue window, or accumulating inactivity that eventually feeds into a future reclassification if the pattern continues across multiple cycles.
